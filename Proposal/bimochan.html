Bimochan's Experiment Plan

Nepali Fuzzy Phonemes — my individual slice of the group project, scoped for solo execution now and merge into bimochanbranch.html / the shared pipeline later.

Scope of this file: this is my part only — data prep + fuzzy/probabilistic phoneme classification, with Gaussian Process Classification as the flagship method. It does not cover teammates' pieces (base ASR fine-tuning, text-mining/context disambiguation, etc.), which live in their own tracking files and get integrated later. See the full proposal for the whole-project picture.

1. What I'm actually building

A pipeline that takes candidate Nepali confusable phoneme pairs, extracts acoustic features from real clips, and classifies them with both a hard baseline and an uncertainty-aware model (fuzzy-logic + Gaussian Process Classification), then checks whether the uncertainty the model reports actually lines up with cases humans find ambiguous.

Deliverable A working notebook/script chain that goes: raw clips → features → baseline classifier → GPC classifier → calibration check, runnable end-to-end on whatever subset of the Layer-2 dataset exists at the time, plus a short results write-up (accuracy, calibration, confusion matrix) I can hand off.

  2. TODO Pull matching clips from whatever's already collected under clips/; if too few speakers exist for the pilot pairs, record a handful myself first rather than waiting on the full community collection pipeline.
  3. TODO Build/borrow the rule-based Devanagari G2P converter (needed to confirm phoneme labels on clips before any classifier training).
  4. TODO Run forced alignment (or a rough manual boundary mark if no Nepali-capable aligner is available yet) to get phoneme-level segment boundaries.
  5. TODO Extract features: MFCCs + deltas, formants (F1–F3), VOT, duration, pitch/energy contour. Cache to a feature manifest so every model downstream reads the same file.
  6. TODO Train the hard-boundary baseline (Random Forest) per pair.
  7. TODO Train fuzzy c-means / fuzzy k-NN on the same features.
  8. TODO Train GPC (start with GPflow, RBF kernel, Laplace approximation) per pair — this is the core of my contribution.
  9. TODO Collect a small human-ambiguity rating set myself (2–3 raters, forced-choice + confidence, on the pilot pairs only) to have a real calibration target, even at small scale.
  10. TODO Compare baseline vs. fuzzy vs. GPC on accuracy, and GPC's posterior variance vs. human disagreement (the calibration check).
  11. TODO Write up pilot results — this becomes the evidence base for the full proposal's Layer 2/3 sections and the thing I hand off for integration.

4. Pipeline sketch

clips/<pair_id>/<speaker_id>_<word>.wav
    │
    ▼
[QC + normalize: 16kHz mono, trim silence, dedupe]
    │
    ▼
[forced alignment → phoneme boundaries]
    │
    ▼
[feature extraction: MFCC, formants, VOT, duration, pitch/energy]
    │
    ├──► [baseline: Random Forest, hard label]
    ├──► [fuzzy: c-means / fuzzy k-NN, membership scores]
    └──► [GPC: RBF/Matérn kernel, Laplace approx, posterior + variance]
                │
                ▼
    [compare vs. human ambiguity ratings → calibration check]
                │
                ▼
        results write-up (accuracy, F1, ECE, confusion matrix)

5. Tooling I'll use

  • librosa / praat-parselmouth — feature extraction (formants, VOT-style measurements)
  • scikit-learn — Random Forest baseline
  • scikit-fuzzy — fuzzy c-means / fuzzy k-NN
  • GPflow (or GPyTorch if I end up needing GPU-backed sparse GP) — Gaussian Process Classification
  • scipy.stats — Spearman correlation for the uncertainty-vs-human-disagreement check
  • Montreal Forced Aligner, or a manual boundary-marking fallback if no Nepali acoustic model is available

6. What "done" looks like for my part

Minimum: baseline vs. GPC comparison on the 8 pilot pairs, with accuracy + a calibration plot, reproducible from a single script.

Good: the above plus fuzzy-logic as a third comparison arm, and the human-ambiguity correlation check actually run (not just planned).

Stretch (only if time allows before integration): feed my GPC uncertainty scores into a toy downstream disambiguation test, to have a first RQ5-style result ready before merging with the group's ASR/text-mining pieces.

7. Integration notes for later (→ bimochanbranch.html)

This file is the solo-execution plan. When it's time to integrate with the rest of the group's work, the merge point is: my GPC/fuzzy uncertainty scores become an input feature to whatever confusable-word disambiguation classifier the group builds on top of ASR N-best output (per §14 of the full proposal). Concretely, that means my output manifest needs to expose, per phoneme token: pair_id, predicted_label, posterior_probability, posterior_variance, fuzzy_membership_score — in a stable schema so it plugs into bimochanbranch.html's pipeline without a rewrite. I'll keep that schema fixed once the pilot works, even if the pair list grows.
